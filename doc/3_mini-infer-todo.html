手写 KV Cache（不重算）

理解并手动实现 KV Cache 机制，让 decode 阶段不再重算 prefix 的 attention，这是推理引擎最基础的加速手段。

理解 KV Cache 原理
⏱ 0.5 天

📌 要做什么

  • 搞懂为什么 decode 时每个新 token 要重算所有历史 KV 是 O(n²)
  • 理解 prefill 阶段一次性算完所有 KV，decode 阶段只算新 token 的 KV 并 append
  • 画出 KV Cache 的内存布局图（每层、每头、seq_len 维度）

🧠 核心公式

# 标准 attention (无 cache) Q = X @ W_q # (1, seq, dim) K = X @ W_k # (1, seq, dim) V = X @ W_v # (1, seq, dim) scores = Q @ K.T / sqrt(d_head) # (1, seq, seq) — 每步都重算！ out = softmax(scores) @ V # 有 KV Cache 后 (decode 阶段) K_cache = [K_0, K_1, ..., K_{t-1}] # 已缓存 K_new = x_t @ W_k # 只算当前步 K = concat(K_cache, K_new) # (1, t+1, dim) # Q 也只有当前步 (1, 1, dim)，attention 是 (1, 1, t+1)
阶段Q 形状K/V 形状计算量
Prefill(1, S, D)(1, S, D)O(S²D)
Decode (无 cache)(1, 1, D)(1, S, D) 重算O(SD) 每步
Decode (有 cache)(1, 1, D)append 到 cacheO(SD) 但 KV 不重算

✅ 验收标准

  • 能在白板上画出 prefill → decode → decode → ... 的 KV Cache 数据流
  • 能解释为什么 cache 后 decode 是 memory-bound 而非 compute-bound
  • 写下一份笔记 kv_cache_notes.md
实现手动 KV Cache 推理
⏱ 2 天

📌 要做什么

  • 不用 model.generate()，自己写 forward loop
  • Prefill 阶段：一次性算完所有 prompt token 的 KV，存入 cache
  • Decode 阶段：每步只前向 1 个 token，从 cache 读历史 KV，append 新 KV
  • Cache 形状：(num_layers, 2, batch, num_heads, max_seq, head_dim)

🛠 怎么做

# mini_infer/kv_cache.py import torch class KVCache: """手动 KV Cache，预分配最大长度""" def __init__(self, num_layers, num_heads, max_seq, head_dim, dtype=torch.float16, device="musa"): self.num_layers = num_layers self.max_seq = max_seq self.device = device # (L, 2, num_heads, max_seq, head_dim) self.k = torch.zeros(num_layers, num_heads, max_seq, head_dim, dtype=dtype, device=device) self.v = torch.zeros(num_layers, num_heads, max_seq, head_dim, dtype=dtype, device=device) self.seq_len = 0 # 当前已缓存长度 def update(self, layer_idx, k_new, v_new): """k_new: (num_heads, 1, head_dim) — decode 阶段""" s = self.seq_len self.k[layer_idx, :, s] = k_new.squeeze(1) self.v[layer_idx, :, s] = v_new.squeeze(1) self.seq_len += 1 def get_kv(self, layer_idx): """返回当前所有缓存的 KV""" s = self.seq_len return self.k[layer_idx, :, :s], self.v[layer_idx, :, :s]
# mini_infer/forward.py — 手动 decode loop def generate_with_cache(model, tokenizer, prompt, max_new=256): # === Prefill === input_ids = tokenizer(prompt, return_tensors="pt").input_ids.to("musa") cache = KVCache( num_layers=model.config.num_hidden_layers, num_heads=model.config.num_attention_heads, max_seq=input_ids.shape[1] + max_new, head_dim=model.config.hidden_size // model.config.num_attention_heads, ) # 手动逐层 forward (prefill) hidden = model.embed(input_ids) # 伪代码，实际要调各层 for i, layer in enumerate(model.layers): q, k, v = layer.attn.qkv(hidden) # reshape to (num_heads, seq, head_dim) cache.k[i, :, :k.shape[1]] = k cache.v[i, :, :v.shape[1]] = v cache.seq_len = k.shape[1] # attention with full KV hidden = layer.attn.output(hidden, cache.get_kv(i)) hidden = layer.mlp(hidden) # === Decode loop === next_token = sample(model.lm_head(hidden[:, -1])) output_ids = [next_token.item()] for _ in range(max_new - 1): hidden = model.embed(next_token.unsqueeze(0)) for i, layer in enumerate(model.layers): q, k, v = layer.attn.qkv(hidden) # k,v: (1, 1, dim) cache.update(i, k, v) kv_k, kv_v = cache.get_kv(i) hidden = layer.attn.output(hidden, (kv_k, kv_v)) hidden = layer.mlp(hidden) logits = model.lm_head(hidden[:, -1]) next_token = sample(logits) output_ids.append(next_token.item()) return output_ids
难点：Qwen3 用的是 RMSNorm + RoPE + GQA（grouped-query attention），K/V 的头数可能少于 Q 的头数。cache 只缓存 K/V 的实际头数，attention 时再 repeat 或 broadcast。

Continuous Batching（连续批处理）

静态 batch 会等最慢的请求结束才能释放 batch，Continuous Batching 让每个 decode 步动态组 batch，吞吐可提升 3-5×。

理解 Continuous Batching 调度逻辑
⏱ 0.5 天

📌 要做什么

  • 搞懂为什么静态 batching 浪费：batch 中某个请求先结束，其余请求独占 batch slot
  • 理解 iteration-level scheduling：每个 decode step 重新组 batch
  • 理解 request 生命周期：WAITING → RUNNING → FINISHED
策略组 batch 时机空闲等待吞吐
静态 Batching请求入队时严重（等最长请求）低
Dynamic Batching每个 step较少中
Continuous Batching每个 iteration几乎无高
# 调度状态机 class RequestState: WAITING = "waiting" # 在队列中等待被调度 RUNNING = "running" # 正在参与 decode FINISHED = "finished" # 生成结束（EOS / max_len） # 每个 iteration: # 1. 把 WAITING 中能塞进 batch 的请求提到 RUNNING # 2. 对所有 RUNNING 请求做一次 forward # 3. 采样、append token # 4. 检查 EOS，FINISHED 的释放 slot

✅ 验收标准

  • 能画出调度时序图：请求 A/B/C 在不同时间到达，batch 组成如何变化
  • 理解 max_num_seqs / max_tokens_per_batch 两个约束
实现 Continuous Batch 调度器 + 改造 forward
⏱ 3 天

📌 要做什么

  • 写一个 Scheduler 类，管理请求队列和 batch 组装
  • 改造 forward：支持变长 batch（不同请求不同 seq_len），用 attention mask 隔离
  • 每个 iteration 只对 RUNNING 请求做一步 decode
  • 新请求随时可加入（模拟流式）

🛠 核心代码结构

# mini_infer/scheduler.py class Request: def __init__(self, req_id, prompt_ids, max_new_tokens): self.req_id = req_id self.prompt_ids = prompt_ids self.output_ids = [] self.state = RequestState.WAITING self.num_generated = 0 self.max_new_tokens = max_new_tokens class Scheduler: def __init__(self, max_num_seqs=8, max_total_tokens=16384): self.waiting: list[Request] = [] self.running: list[Request] = [] self.max_num_seqs = max_num_seqs self.max_total_tokens = max_total_tokens def schedule(self): """每个 iteration 调用，返回本步要跑的 batch""" # 1. 把 waiting 中能塞的塞进 running available = self.max_num_seqs - len(self.running) for req in self.waiting[:available]: total_tokens = sum(len(r.prompt_ids) + r.num_generated + 1 for r in self.running + [req]) if total_tokens > self.max_total_tokens: break req.state = RequestState.RUNNING self.running.append(req) self.waiting.remove(req) return self.running def post_step(self, running_outputs): """处理本步输出，标记 finished""" for req, token in zip(self.running, running_outputs): req.output_ids.append(token) req.num_generated += 1 if token == EOS or req.num_generated >= req.max_new_tokens: req.state = RequestState.FINISHED # 清理 finished self.running = [r for r in self.running if r.state == RequestState.RUNNING]
# mini_infer/engine.py — 主循环 class MiniInferEngine: def __init__(self, model, tokenizer, scheduler): self.model = model self.tokenizer = tokenizer self.scheduler = scheduler # 每个请求一个独立的 KV Cache slice self.caches: dict[int, KVCache] = {} def step(self): """执行一个 iteration""" batch = self.scheduler.schedule() if not batch: return [] # 收集 batch 中每个请求的 last token input_ids = torch.stack([ torch.tensor(req.prompt_ids + req.output_ids, device="musa")[-1].unsqueeze(0) for req in batch ], dim=0) # (B, 1) # 逐层 forward（batch 维度并行） hidden = self.model.embed(input_ids) for i, layer in enumerate(self.model.layers): q, k, v = layer.attn.qkv(hidden) # 写入各自的 cache for b, req in enumerate(batch): self.caches[req.req_id].update(i, k[b:b+1], v[b:b+1]) # 读取各自的 KV 做 attention # ... (需要处理变长 attention) hidden = layer.mlp(hidden) logits = self.model.lm_head(hidden[:, -1]) next_tokens = logits.argmax(dim=-1) self.scheduler.post_step(next_tokens.tolist()) return next_tokens.tolist()
关键难点：变长 attention。batch 中不同请求的 KV Cache 长度不同，不能直接做统一矩阵乘法。方案：
(1) pad 到同一长度 + attention mask（简单但浪费）
(2) 用 FlashAttention 的 varlen 接口（高效但需要 kernel 支持）
(3) 逐请求串行 attention 但 batch 矩阵乘（折中）

Paged KV Cache（类虚拟内存管理）

用固定大小的 block 管理 KV Cache，消除碎片，支持任意长度序列的高效内存复用。这是 vLLM 的核心创新。

理解 PagedAttention 原理
⏱ 0.5 天

📌 要做什么

  • 理解传统 KV Cache 的内存碎片问题：不同请求长度不同 → 内部碎片 + 外部碎片
  • 理解 block 化：把 KV Cache 切成固定大小 block（如每 block 16 token）
  • 理解 block table：逻辑 block → 物理 block 的映射（类似 OS 页表）
  • 理解 copy-on-write：多请求共享 prefix 时只复制 block 指针
方案内存利用率碎片共享 prefix
连续分配~40-60%严重不支持
预分配最大~30-50%内部碎片不支持
Paged (block=16)> 95%极少支持 CoW
# Block 管理核心概念 NUM_BLOCKS = 1024 # 物理 block 总数 BLOCK_SIZE = 16 # 每 block 16 个 token BLOCK_BYTES = 2 * num_layers * num_kv_heads * BLOCK_SIZE * head_dim * 2 # 每个请求维护一个 block_table: List[int] # block_table[i] = 物理 block 编号，存第 i 个逻辑 block # 逻辑 block 0 → 物理 block 42 → token 0~15 的 KV # 逻辑 block 1 → 物理 block 7 → token 16~31 的 KV

# mini_infer/block_allocator.py class BlockAllocator: def __init__(self, num_blocks, block_size, num_layers, num_kv_heads, head_dim, dtype=torch.float16, device="musa"): self.num_blocks = num_blocks self.block_size = block_size self.free_blocks = set(range(num_blocks)) self.allocated = {} # block_id → ref_count # 预分配所有物理 block 的 KV 存储 # (num_blocks, 2[K/V], num_layers, num_kv_heads, block_size, head_dim) self.kv_pool = torch.zeros( num_blocks, 2, num_layers, num_kv_heads, block_size, head_dim, dtype=dtype, device=device ) def allocate(self, num_blocks_needed) -> list[int]: if len(self.free_blocks) < num_blocks_needed: raise MemoryError("Out of KV blocks!") blocks = [self.free_blocks.pop() for _ in range(num_blocks_needed)] for b in blocks: self.allocated[b] = 1 return blocks def free(self, block_ids: list[int]): for bid in block_ids: self.allocated[bid] -= 1 if self.allocated[bid] == 0: del self.allocated[bid] self.free_blocks.add(bid) def get_kv_slice(self, block_id, kv_idx) -> torch.Tensor: """返回某 block 的 K 或 V 张量视图""" return self.kv_pool[block_id, kv_idx] # (L, H, block_size, head_dim)
# mini_infer/paged_kv.py class PagedKVCache: def __init__(self, allocator: BlockAllocator, req_id): self.allocator = allocator self.req_id = req_id self.block_table: list[int] = [] self.num_tokens = 0 def append(self, k_new, v_new): """k_new: (num_layers, num_kv_heads, 1, head_dim)""" if self.num_tokens % self.allocator.block_size == 0: # 需要新 block new_blocks = self.allocator.allocate(1) self.block_table.extend(new_blocks) block_idx = self.num_tokens // self.allocator.block_size offset = self.num_tokens % self.allocator.block_size phys_block = self.block_table[block_idx] # 写入物理存储 self.allocator.kv_pool[phys_block, 0, :, :, offset] = k_new.squeeze(2) self.allocator.kv_pool[phys_block, 1, :, :, offset] = v_new.squeeze(2) self.num_tokens += 1 def get_continuous_kv(self, layer_idx) -> tuple[torch.Tensor, torch.Tensor]: """拼接所有 block 的 KV 为连续张量（用于 attention 计算）""" ks = [] vs = [] for bid in self.block_table: ks.append(self.allocator.kv_pool[bid, 0, layer_idx]) vs.append(self.allocator.kv_pool[bid, 1, layer_idx]) return torch.cat(ks, dim=1)[:self.num_tokens], torch.cat(vs, dim=1)[:self.num_tokens]
性能提示：get_continuous_kv 里的 torch.cat 会产生拷贝开销。生产级实现应该直接用 block_table 做 gather 或写 PagedAttention kernel。但作为教学版，先 cat 跑通正确性，后面再优化。

Chunked Prefill（分块预填充）

长 prompt 的 prefill 会阻塞 decode 请求。把 prefill 切成小块，和 decode 交错执行，降低尾延迟。

理解 Chunked Prefill 原理
⏱ 0.5 天

📌 要做什么

  • 理解 prefill 是 compute-bound，decode 是 memory-bound
  • 理解长 prompt（如 8K token）一次性 prefill 会阻塞所有 decode 请求几百毫秒
  • 理解 chunked prefill：把 prompt 切成 chunk_size=512 的块，每块之间让 decode 请求插队
策略TTFT (长 prompt)Decode 延迟影响GPU 利用率
无 chunk低（一次算完）严重阻塞脉冲式
Chunked (512)略高（分步）几乎无影响平稳

✅ 验收标准

  • 能解释为什么 chunked prefill 牺牲了一点 TTFT 但大幅改善 decode 尾延迟
  • 能画出 chunked prefill 和 decode 交错的 timeline
实现 Chunked Prefill
⏱ 2 天

📌 要做什么

  • 改造 scheduler：prefill 请求按 chunk 分步处理
  • 每个 iteration 先处理一个 chunk 的 prefill，再处理 decode
  • chunk 大小可配置（默认 512 或 1024）
# 在 Scheduler.schedule() 中加入 chunked prefill 逻辑 def schedule_chunked(self, chunk_size=512): batch = [] # 1. 选一个 prefill 请求，只取一个 chunk for req in self.waiting: if req.state == RequestState.WAITING: remaining = len(req.prompt_ids) - req.num_prefilled chunk = req.prompt_ids[req.num_prefilled : req.num_prefilled + chunk_size] req.current_chunk = chunk req.num_prefilled += len(chunk) batch.append(req) if req.num_prefilled >= len(req.prompt_ids): req.state = RequestState.RUNNING # prefill 完成 break # 每步只处理一个 prefill chunk # 2. 加入 decode 请求（如果还有容量） available = self.max_num_seqs - len(batch) for req in self.running[:available]: batch.append(req) return batch
# forward 时区分 prefill chunk 和 decode step def forward_batch(model, batch, caches): prefill_inputs = [] decode_inputs = [] prefill_reqs = [] decode_reqs = [] for req in batch: if hasattr(req, 'current_chunk') and req.current_chunk is not None: prefill_inputs.append(req.current_chunk) prefill_reqs.append(req) else: decode_inputs.append(req.output_ids[-1]) decode_reqs.append(req) outputs = [] # Prefill chunk: 正常前向，写入 KV cache if prefill_inputs: chunk_tensor = torch.tensor(prefill_inputs[0], device="musa").unsqueeze(0) hidden = model.forward_prefill(chunk_tensor, layer_idx=0) # ... 逐层 forward，写入 cache # 只取最后一个 token 的 logits（用于采样下一个 chunk 的第一个 token） # Decode: 单 token 前向 if decode_inputs: decode_tensor = torch.stack([torch.tensor(t, device="musa") for t in decode_inputs]) hidden = model.forward_decode(decode_tensor, caches, decode_reqs) logits = model.lm_head(hidden) outputs.extend(logits.argmax(dim=-1).tolist()) return outputs

✅ 验收标准

  • 长 prompt（4K+）的 prefill 不再阻塞 decode 请求
  • decode 请求的 TPOT 在 prefill 期间波动 < 20%
  • 输出正确性不变
  • 对比有无 chunked 的 TTFT 和 decode 延迟曲线

编写 RMSNorm TileLang Kernel
⏱ 3 天

📌 要做什么

  • RMSNorm 公式：y = x / RMS(x) * γ，其中 RMS(x) = sqrt(mean(x²) + ε)
  • 这是 memory-bound 操作（每字节读一次做平方，再读一次做归一化）
  • 用 TileLang 写融合 kernel：一次遍历完成平方和 + 归一化 + 缩放
  • 对比 PyTorch 原生 RMSNorm 的带宽利用率

🛠 PyTorch 参考实现（要替换掉的）

# 这是 PyTorch 版（慢路径） def rmsnorm_pytorch(x, gamma, eps=1e-6): # x: (B, S, D) gamma: (D,) rms = torch.sqrt(x.pow(2).mean(dim=-1, keepdim=True) + eps) return x / rms * gamma

🛠 TileLang Kernel 骨架

# kernel/rmsnorm_tilelang.py import tilelang import tilelang.language as T # RMSNorm 是 row-wise 操作：每行独立计算 # 关键优化：用 warp-level reduce 算 mean(x^2)，避免多次全局内存访问 def rmsnorm_kernel(B, S, D, eps=1e-6): # 每个 thread block 处理一行 (一个 token 的 D 维向量) # 或者一个 block 处理多行以提高 occupancy @tilelang.jit def kernel(X: T.Tensor[(B, S, D), "float16"], Gamma: T.Tensor[(D,), "float16"], Y: T.Tensor[(B, S, D), "float16"]): for b, s in T.grid(B, S): # Step 1: 计算 sum(x^2) — warp reduce local_sum = T.cast(0.0, "float32") for d in range(D): val = T.cast(X[b, s, d], "float32") local_sum += val * val # Warp-level reduction (TileLang 内置) sum_sq = T.warp_reduce(local_sum, op="sum") # Step 2: 计算 RMS rms = T.sqrt(sum_sq / T.cast(D, "float32") + T.cast(eps, "float32")) # Step 3: 归一化 + 缩放 for d in range(D): Y[b, s, d] = T.cast( T.cast(X[b, s, d], "float32") / rms * T.cast(Gamma[d], "float32"), "float16" ) return kernel # 编译 & 测试 B, S, D = 2, 2048, 4096 # Qwen3-8B hidden_size=4096 kernel = rmsnorm_kernel(B, S, D) x = torch.randn(B, S, D, dtype=torch.float16, device="musa") gamma = torch.randn(D, dtype=torch.float16, device="musa") y = kernel(x, gamma)
注意：以上是 TileLang 的伪代码风格，实际 API 以摩尔线程官方文档为准。关键是理解 RMSNorm 的优化思路：
1. 减少全局内存访问次数（从 ~3 次降到 ~1 次）
2. 用 shared memory 做 warp reduce
3. FP32 累加避免精度损失

# kernel/bench_kernel.py — 带宽测试 import time def measure_bandwidth(func, *args, num_warmup=10, num_iter=100): # Warmup for _ in range(num_warmup): func(*args) torch_musa.synchronize() # Measure t0 = time.perf_counter() for _ in range(num_iter): func(*args) torch_musa.synchronize() elapsed = (time.perf_counter() - t0) / num_iter # 计算带宽：读 X + 读 Gamma + 写 Y B, S, D = args[0].shape bytes_per_call = (B * S * D * 2) + (D * 2) + (B * S * D * 2) bandwidth_gb_s = bytes_per_call / elapsed / 1e9 return bandwidth_gb_s # S5000 理论带宽约 800-900 GB/s (查实际规格) pytorch_bw = measure_bandwidth(rmsnorm_pytorch, x, gamma) kernel_bw = measure_bandwidth(tilelang_kernel, x, gamma) print(f"PyTorch RMSNorm: {pytorch_bw:.1f} GB/s") print(f"TileLang RMSNorm: {kernel_bw:.1f} GB/s") print(f"Speedup: {kernel_bw/pytorch_bw:.2f}×")
